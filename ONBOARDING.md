**Purpose of this document:** Single entry-point for understanding the repository — functional purpose, technical architecture, domain model, key decisions, and where to find more detail. Designed to fit in one AI context window.

---

## 1. What This Platform Is

AGRIFLOW-AI is an **Agricultural Intelligence Platform** — a Python/FastAPI backend that transforms agricultural farm data into decision intelligence. It serves farmers, agronomists, cooperatives, and food supply chain operators.

**Core proposition:** Centralise observational data (soil, weather, telemetry, yield, disease, satellite) into a governed domain model, then layer decision intelligence (recommendations, alerts) on top. Long-term target is a Digital Twin of every farm field with a GaaS Farm Copilot.

**Current state (Phase 13 — October 2026):** The platform has completed its full data domain model and its first AI Decision Intelligence layer. Thirteen development phases are complete; three remain (ML engines, Digital Twin, GaaS).

## 3. Architecture Pattern — Five-Layer Clean Architecture

Every domain in the codebase follows the same five-layer pattern. Dependencies flow strictly inward; no layer skips a layer.

```
Client (HTTP)
    │
    ▼
┌─────────────────────────────────────────────────┐
│  Router          app/api/{domain}/router.py      │  HTTP, status codes, schema→ORM
├─────────────────────────────────────────────────┤
│  Schema          app/schemas/{domain}.py         │  Pydantic request/response contracts
├─────────────────────────────────────────────────┤
│  Service         app/services/{domain}.py        │  Business rules, domain exceptions
├─────────────────────────────────────────────────┤
│  Repository      app/db/repositories/{domain}.py │  SQLAlchemy queries only
├─────────────────────────────────────────────────┤
│  Model           app/db/models/{domain}.py       │  ORM class + AuditableModel mixin
├─────────────────────────────────────────────────┤
│  Database        PostgreSQL + TimescaleDB        │
└─────────────────────────────────────────────────┘
```

**Key conventions:**
- `AuditableModel` mixin provides `id UUID PK`, `created_at TIMESTAMPTZ`, `updated_at TIMESTAMPTZ` on every entity
- `BaseRepository[ModelT]` provides generic CRUD; domain repositories extend it with domain-specific queries
- `app/api/deps.py` owns session lifecycle (open → commit on success, rollback on exception) and all service factory functions
- Shared enums live in `app/core/enums.py` — imported across domains without circular dependencies

## 4. Domain Model — All 12 Domains

### Hierarchy

```
Farm  ──────────────────────────────────────────── (root aggregate)
└── Field  ─────────────────────────────────────── (geospatial entity)
     ├── Crop  ──────────────────────────────────── (lifecycle object: PLANNED→HARVESTED)
     │    ├── YieldRecord          [hypertable]   (harvest intelligence, primary AI label)
     │    └── DiseaseObservation   [hypertable]   (plant health, AI disease label)
     ├── SoilProfile        (1:1)                 (soil intelligence profile)
     ├── WeatherRecord            [hypertable]   (climate time-series)
     ├── SensorReading  (append-only) [hypertable] (IoT telemetry, immutable)
     ├── IrrigationEvent  (mutable)   [hypertable] (operational management event)
     ├── SatelliteObservation (mutable) [hypertable] (Earth observation, field-anchored)
     ├── Recommendation   (mutable)               (AI decision output — Phase 13)
     └── Alert            (mutable)               (operational alert — Phase 13)
```

### Domain Descriptions

| Domain | Type | Key Facts |
|---|---|---|
| **Farm** | Root aggregate | `farm_code` unique; `latitude/longitude`; full CRUD resolved Phase 13 |
| **Field** | Geospatial entity | Belongs to Farm; `area_hectares`, `soil_type`, `elevation_m` (AI attr) |
| **Crop** | Lifecycle object | `CropStatus` state machine (PLANNED→PLANTED→GROWING→HARVESTED); belongs to Field |
| **SoilProfile** | 1:1 with Field | Lab-grade NPK columns `NUMERIC(8,4)`; UNIQUE FK enforced at DB + service |
| **WeatherRecord** | Time-series | `recorded_at TIMESTAMPTZ NOT NULL`; `data_source` provenance; hypertable |
| **SensorReading** | Append-only telemetry | No PATCH/PUT (ADR-007-27); 11-value `SensorType` enum; hypertable |
| **IrrigationEvent** | Mutable operational event | `started_at/ended_at`; cross-field sparse-PATCH guard; hypertable |
| **YieldRecord** | Grandchild (Crop-anchored) | Dual-FK: `crop_id` primary + `field_id` denormalized; `measurement_method` provenance |
| **DiseaseObservation** | Grandchild (Crop-anchored) | `DiseaseSeverity` (LOW/MEDIUM/HIGH/CRITICAL); `DiagnosisMethod` enum |
| **SatelliteObservation** | Field-anchored Earth obs. | 8 providers, 8 spectral indices (NDVI/EVI/NDWI…); AI-oriented query endpoints |
| **Recommendation** | Decision output | 6 types, 6 statuses, 3 priorities; `confidence_score NUMERIC(4,3)`; `engine_version VARCHAR(50)` |
| **Alert** | Operational alert | 10 types, 4 severities; `triggered_at TIMESTAMPTZ NOT NULL` (event detection ≠ `created_at`) |

## 5. Database Layout

### Storage Model

| Table | Storage | Introduced |
|---|---|---|
| `farms` | PostgreSQL (relational) | Phase 1 |
| `fields` | PostgreSQL (relational) | Phase 2 |
| `crops` | PostgreSQL (relational) | Phase 3 |
| `soil_profiles` | PostgreSQL (relational) | Phase 4 |
| `recommendations` | PostgreSQL (relational) | Phase 13 |
| `alerts` | PostgreSQL (relational) | Phase 13 |
| `weather_records` | TimescaleDB hypertable | Phase 5 / 12 |
| `sensor_readings` | TimescaleDB hypertable | Phase 7 / 12 |
| `irrigation_events` | TimescaleDB hypertable | Phase 8 / 12 |
| `yield_records` | TimescaleDB hypertable | Phase 9 / 12 |
| `disease_observations` | TimescaleDB hypertable | Phase 10 / 12 |
| `satellite_observations` | TimescaleDB hypertable | Phase 11 / 12 |

**Why Recommendation/Alert are standard PostgreSQL (not hypertables):** Low-volume mutable decision records. TimescaleDB hypertables are optimised for high-frequency append-only time-series. Applying hypertable partitioning to a table with dozens of rows per day that requires frequent updates would add partitioning overhead with no benefit. (ADR-013 Decision Layer Pattern)

**TimescaleDB platform (Phase 12):** 6 hypertables with composite PKs `(id UUID, time_column TIMESTAMPTZ)`, 6 compression policies, 8 continuous aggregates (`time_bucket()` rollups), 11 retention policies with domain-tiered lifecycles.

**Migrations:** 18 Alembic revisions; HEAD = `h2i3j4k5l6m7`. Apply with `alembic upgrade head`.

### Shared Enum Registry (`app/core/enums.py`)

14 enums defined once and imported across all domains:

`SensorType` · `IrrigationMethod` · `WaterSource` · `YieldMeasurementMethod` · `DiseaseSeverity` · `DiagnosisMethod` · `SatelliteProvider` · `SpectralIndex` · `ProcessingLevel` · `RecommendationType` · `RecommendationStatus` · `RecommendationPriority` · `AlertType` · `AlertSeverity`

All use `str`-inheriting enum pattern (ADR-003-01): values are human-readable strings, not opaque integer codes.

## 7. Key Architectural Decisions (ADR Summary)

These are the decisions most likely to surprise a reader encountering the codebase for the first time.

| ADR | Decision | Why |
|---|---|---|
| ADR-001-01 | UUID v4 primary keys everywhere | Distribution-safe; no coordination required for ID generation |
| ADR-001-02 | `AuditableModel` mixin on every entity | Audit timestamps are non-negotiable from day one; retrofitting is expensive |
| ADR-001-03 | Alembic as sole schema change mechanism | Reproducible schema state across environments; no ad-hoc DDL |
| ADR-003-01 | `str`-inheriting enums | Human-readable database values; compatible with OpenAPI string serialisation |
| ADR-007-27 | `SensorReading` append-only (no PATCH/PUT) | Telemetry is factual history; corrections belong in new records, not overwrites |
| ADR-007-26 | Service layer event extension points | Explicit integration boundary reserved for Redpanda; not wired yet |
| ADR-009-01 | `YieldRecord` anchored to `crop_id` | Yield is a per-crop-cycle measurement; field is secondary context |
| ADR-009-02 | Denormalized `field_id` on `YieldRecord` | Enables field-scoped yield queries without JOIN through `crops` |
| ADR-010-02 | Denormalized `field_id` on `DiseaseObservation` | Same pattern — direct field-scoped disease history |
| ADR-011-01 | `SatelliteObservation` field-anchored | Earth observation covers the field boundary regardless of crop lifecycle |
| ADR-013-01/02 | `crop_id` nullable SET NULL on Recommendation/Alert | Recommendations are field-level entities; crop context is optional |
| ADR-013-03 | `triggered_at` mandatory on `Alert` | Event detection time is distinct from database persistence time (`created_at`) |
| ADR-013-04 | `confidence_score NUMERIC(4,3)` | Exact decimal arithmetic for ML threshold comparisons; FLOAT accumulates rounding error |
| ADR-013-05 | `engine_version VARCHAR(50)` on Recommendation | ML model provenance — disputes require knowing which model version fired |
| ADR-013 (pattern) | Recommendation/Alert use standard PostgreSQL | Decision records are low-volume and mutable; hypertable partitioning would add overhead with no benefit |
